# 长截图排错记录

记录 2026-11 这一轮长截图拼接问题的定位过程、根因和修复。基线是提交 `f6ee778`（抽出 `ScrollSession` 状态机），本文涉及的改动目前尚未提交。

## 1. 现象汇总

按出现顺序，用户反馈了四类问题：

| # | 现象 | 涉及环节 |
| --- | --- | --- |
| 1 | 滚动一会儿后不再拼接，只截到一部分 | 重叠检测阈值、重锚策略 |
| 2 | 完全没滚动，也会无限往下拼接 | 静止判定、评分的绝对可靠性 |
| 3 | 已经滚到页面底部，部分应用继续回弹，于是"滚一下就拼一下" | 到底/回弹识别 |
| 4 | 结果首屏有蓝色边框；左侧出现黑色色块 | 首帧时机、侧边栏定位 |

问题 1 在 `f6ee778` 里已经处理，问题 2~4 是后续几轮修复的内容。

## 2. 排错方法：先让问题可复现

这类问题的共同难点是"只靠口头描述，无法定位到具体帧"。所以在改算法之前，先补了一套录制 + 离线重放的调试链路。

### 2.1 抓帧导出

```bash
LUMESHOT_SCROLL_DEBUG=1 ./build/lumeshot
# 或指定目录
LUMESHOT_SCROLL_DEBUG=/tmp/lsumeshots ./build/lumeshot
```

每次长截图会话生成一个带时间戳的子目录（默认 `$TMPDIR/lumeshot-scroll/`）：

| 文件 | 内容 |
| --- | --- |
| `frames/frame_0001.png…` | 每 200ms 抓到的原始画面，按顺序编号 |
| `scroll.log` | 每帧一行判定：`outcome`、`overlap`、`misses`、尺寸、已拼接高度 |
| `result.png` | 本次会话最终合成的长图 |

`scroll.log` 采样：

```text
frame=1 outcome=appended overlap=0 misses=0 size=1440x900 total=900
frame=2 outcome=no-scroll overlap=-1 misses=0 size=1440x900 total=900
frame=3 outcome=appended overlap=660 misses=0 size=1440x900 total=1140
```

### 2.2 离线重放

```bash
./build/lumeshot-replay /tmp/lumeshot-scroll/20260101-120000
```

`lumeshot-replay` 复用同一个 `ScrollSession`，把导出目录里的帧按顺序重放一遍，输出与 `scroll.log` 相同格式的逐帧判定，并写出 `replay.png`。

这套机制的价值：

- 用户只需复现一次并交出目录，之后不需要再手动滚动；
- 算法改动可以在同一份真实数据上前后对比，判断是修好了还是换了个错法；
- 能区分"输入帧本身有问题"（`frames/` 里有黑块）和"合成有问题"（只有 `result.png` 有黑块）。

本次问题 4 正是靠这个区分思路定位的：黑块在每一帧里都有，说明是抓屏内容被污染，而不是合成逻辑出错。

## 3. 问题与处理

### 3.1 滚动一会儿后停止拼接（已修，`f6ee778`）

三个独立原因叠加：

1. **并列容差过大**：原实现在误差相差 0.5 以内就当作并列并取更大的重叠，导致每次少拼几行，误差逐渐累积。
2. **纹理门槛过高**：50% 的纹理行占比要求会拒绝窄栏文章、偏侧内容。
3. **锚点不更新**：连续丢帧后锚点永远停在旧画面，之后所有帧都对不上，彻底停止。

对应改动：

- 增加 `strictError`（不做像素容差）用于区分相邻偏移，只有严格误差真正并列才取更大重叠；
- 纹理门槛降到 25%，每栏候选数 3 → 5；
- 连续 3 帧无法重叠且画面有纹理时，以当前帧重新锚点；低纹理画面不重锚，保留空白压缩行为。

### 3.2 不滚动也无限拼接（已修）

原判定用"整帧平均误差"判断画面是否变化，光标闪烁、动画、渐变都会让平均值超过阈值，于是每帧都继续走重叠检测。而重叠检测在稀疏页面上很容易凑出一个"看起来还不错"的错位，导致每帧追加几十行。

修复分两步：

1. `stitch::mostlySame()`：按**逐行**比较，单行误差小于 4 视为一致，一致行占比达到 75% 就认为画面基本没动。这样小面积动画不会触发追加。
2. `ScrollSession` 额外保存上一帧原始画面（`m_previousFrame`），在调用 `detectOverlap` 之前先做一次 `stitch::framesMostlySame()`，一致就直接 `NoScroll` 并清零失败计数。

重锚也因此更安全：连续失败只可能发生在"帧确实在变"的情况下。

### 3.3 页面到底后回弹仍在拼接（已修）

弹性滚动（overscroll）在页面到底时继续上滑，内容整体上移、底部露出的是背景而不是新内容。重叠检测看到重叠变小，就认为"又滚动了一点"，于是每滚一下追加一条空白。

修复：追加前检查新增部分是否含有实际内容。

```cpp
// scrollsession.cpp
const QImage piece = normalized.copy(0, overlap, normalized.width(), newRows);
if (!stitch::hasVisibleContent(piece))
    return {Outcome::NoScroll, {}, -1};
```

`stitch::hasVisibleContent()` 把片段缩到 64 宽，以首行为基准逐行比较：文字、图片等内容行的灰度分布必然不同；纯背景、纯色条每行几乎一致，与首行差异不足 4.0 就判定为没有内容。

副作用：滚动经过大片纯色区域时该区域会被压缩掉。这与既有的"空白压缩"行为一致，可以接受。

### 3.4 首屏蓝色边框（已修）

框选遮罩关闭后，合成器还没重绘，第一次抓帧把遮罩的蓝色边框截了进去；而首帧会整屏保留，所以边框留在结果最上方。

修复：首帧延迟 160ms 再抓（`ScrollCapture::kFirstDelayMs`）。边框窗口本身画在选区外侧并挖空了内部，不会进入画面。

### 3.5 长图左侧黑色色块（已修）

根因是侧边栏（`LongCaptureSidebar`）被截进了画面，且有两个叠加因素：

1. **定位用了错误尺寸**。侧边栏高度由布局决定，但代码在 `show()` 之前就调用 `size()`，此时拿到的是 `172×480` 的默认值，而 `adjustSize()` 后的实测尺寸约为 `200×378`。放置判断从一开始就是错的。
2. **四面都没有空间时的兜底是错的**。旧逻辑在右侧放不下时翻到左侧，再用 `qBound` 夹到桌面范围内。侧边栏宽 200、间隙 12，当选区宽度超过"桌面宽度 − 424"（两侧各需 212）时，四个方向都放不下，`qBound` 会把侧边栏贴到桌面最左边，正好压在选区左侧区域，于是每帧都被截进去。

修复：

- 先 `adjustSize()` 再取尺寸；
- 放置顺序改为右 → 左 → 下 → 上，任意一侧能放下就放在选区外；
- 四面都放不下时：侧边栏先在选区左上角提示 0.5 秒，随后移出屏幕。提示期间不抓帧（首帧延迟变成 0.5s + 160ms），避免再次截进首屏。移出屏幕后仍保留键盘焦点，`Enter` 完成、`Esc` 取消；
- 由于窗口移出屏幕后用户可能点击页面导致失焦，再补一条兜底：长截图进行中，托盘菜单顶部出现"完成长截图 / 取消长截图"，抓取结束时自动隐藏。

相关代码：`LongCaptureSession::start()`、`placeSidebarOutside()`、`TrayController::setLongCaptureActive()`。

## 5. 尚未解决的隐患

排错过程中用重放工具做了一次合成页面验证，发现重叠判定存在精度问题，**本轮没有修改**：

- 一张已知偏移 40px（正确重叠 260 行）的页面，`detectOverlap` 返回 264；
- 插桩显示错位到 258 时每行误差几乎全是 `0.000`，但用 Python 直接比对同一组像素平均差约 9；
- 把 `trimmedMean` 的裁剪比例从 1/3 收到 1/10 后，结果变成 261，仍然不精确。

原因有两个，都在 `stitch.cpp`：

1. **精验阶段按行抽样**：`step = max(1, overlap / kFineSamples)`，重叠 260 行时每 2 行才采 1 行，±1 行的偏移完全不可见；
2. **裁剪比例过大**：`trimmedMean` 丢掉最差 1/3 的行。稀疏页面里错位时只有少数行真正不匹配，其余多数是空白行（误差 0），丢掉 1/3 后误差被抹成 0，"错位"和"正确"得分相同，最后由并列仲裁取更大重叠。

影响：每次拼接可能多算/少算 1~4 行，表现为 1px 级重复或丢失，累积后轻微压缩。它不会造成"无限拼接"，但会让接缝不够精确。

### 5.1 真实录制实测

两组录制（`20261125-105707` 普通文章 1298×741、`20261125-105810` 触底回弹界面 789×407）：

| 指标 | 文章 | 回弹界面 |
| --- | --- | --- |
| 帧数 | 61 | 43 |
| 拼接次数 | 20 | 3 |
| 拼接高度 | 5061 px | 1215 px |
| 接缝处 1 行重复 | 15 / 20 | 0 |
| 其中重复行有内容的 | 3（std ≈ 6，低对比度分隔线） | 0 |

- 把每个拼接帧与下一帧在 ±8 行范围内按全宽 MAE 逐一比较，20 个接缝里有 19 个的"最优偏移"与记录值相差 1~8 行，说明判定确实不是像素级最优；但落到结果图上，重复的几乎都是空白行，唯一有内容的 3 处也只是浅色分隔线，肉眼不可见，也没有发现缺行。
- 回弹界面在到达底部后连续 18 帧判定为 `no-scroll`，高度停在 1215 px 不再增长，说明空白条守卫生效；中途因连续失配触发过一次重锚（+407 行），结果内容连续、无重复。

结论：当前精度对实际使用够用，本节记录的问题属于"知道了但暂不修"，留作后续优化。

可能的修法如下。

- 精验之后增加一次"逐行全采样"的精修，只在当前最优候选 ±2 行范围内比较，成本可控；
- 把 `trimmedMean` 的裁剪比例降到 10% 左右，或改为按行对比度加权，让空白行不再被当作"完美匹配"；
- 并列仲裁只在严格误差完全相等时才偏向更大重叠。

## 6. 后续建议

1. 把现有两组真实录制（普通文章、触底回弹）保留为 `lumeshot-replay` 的回归样本，后续再补一组长列表。
2. 在改第 5 节的评分逻辑之前，先用这些样本记录当前 `overlap`，改动后逐帧对比，确认只修正了错位、没有引入新的丢帧。
3. 若真实页面出现"选区几乎占满桌面"的固定用法，可以考虑把托盘兜底升级为更显眼的提示（例如侧边栏隐藏时用托盘气泡告知快捷键）。
